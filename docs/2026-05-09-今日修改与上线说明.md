## 二、核心目标

今天这轮修改围绕两个核心目标：

1. 小红书发文链路降复杂度。
   门店员工只需要先维护一次门店档案，之后发文页只选内容方向，必要时补一句“今天想发什么”，不再让员工理解“软带项目、自然带店、三类门店、求推荐”等复杂植入模式。

2. 生图质量和成本收敛。
   小红书封面和海报生成统一回到 `1k` 基础档位，不再默认走更贵、更慢的 `2k`。同时加强封面信息密度、参考图使用规则和 CTA 禁止规则，减少“只有大标题+背景图”的干瘪画面，也减少“立即进入小程序、关注、私信”等不适合小红书传播的 CTA。

## 三、小红书发文页改动

涉及小程序文件：

- `pages/xiaohongshu/index.js`
- `pages/xiaohongshu/index.wxml`
- `pages/xiaohongshu/index.wxss`
- `pages/store-profiles/index.js`
- `pages/store-profile-editor/index.js`
- `pages/store-profile-editor/index.wxml`
- `utils/config.js`
- `app.json`

### 1. 发文入口简化

发文页从“填写主题 + 选择植入方式 + 补门店信息”的复杂模式，调整为：

- 当前门店档案
- 内容方向：攻略 / 科普 / 避雷 / 对比
- 今天想发（可选）
- 更多设置：关键词 / 表达强度

被移除或隐藏的复杂操作：

- 不再展示“门店植入”选择器。
- 不再让员工选择“不带店、软带项目、自然带店、三类门店、求推荐”。
- 不再要求每次发文都重复填写店名、项目、区域、卖点。
- 不再强制填写主题，不填时后端会根据门店主推项目和内容方向自动补主题。

### 2. 门店档案作为发文前置条件

发文页现在默认要求先选择门店档案：

- 没有门店档案时，主按钮显示“先设置门店档案”。
- 点击生成时会弹窗引导去填写门店档案。
- 有门店档案后，页面展示当前门店、主推项目、区域。
- 员工后续发文只需要切换内容方向即可。

这样做的原因：

- 美业门店做小红书发文，本质上大多是为门店获客服务。
- 让员工每次决定“带店不带店”会增加操作成本，也容易带偏内容。
- 门店档案只填写一次，后续自动参与生成，符合低操作成本的使用场景。

### 3. 门店档案选择链路修复

修复了几个容易造成“错店/旧店信息残留”的问题：

- 从门店档案列表选择门店后，不只保存 `profile_id` 和展示 label，还会保存：
  - `xhs_store_profile_name`
  - `xhs_store_profile_offer`
  - `xhs_store_profile_local`
- 从门店档案编辑页新建或保存后，也会同步写入上述字段。
- 发文页每次 `onShow` 都会重新读取当前门店档案，避免切换门店后页面仍展示旧项目、旧区域。
- 打开旧草稿时，会优先匹配当前已选门店，避免草稿恢复把当前门店摘要覆盖掉。
- 从门店档案编辑页基于旧草稿生成“定制版”时，改为使用当前保存的门店档案，而不是沿用旧草稿里的旧店名。

### 4. 门店档案编辑页重排

门店档案编辑页现在优先让用户填：

1. 门店名称
2. 主推项目名称

城市、区县、地标、门店类型、主推时长放到“更多信息（可选）”里。

调整原因：

- 对店员来说，最重要的是“这家店叫什么”和“这次主要推什么项目”。
- 城市、区县、商圈、承诺等信息有价值，但不应该在第一次填写时造成压力。
- 后续如果要提高本地感，再补充这些可选信息即可。

### 5. 生成超时调整

小程序全局请求和下载超时从 `120000ms` 调整到 `240000ms`。

相关位置：

- `app.json`
- `utils/config.js`
- 发文页内部长任务 timeout
- 海报页内部长任务 timeout

原因：

- 文案生成、封面生成、海报生成都可能受模型排队影响。
- 之前 120 秒容易出现前端超时，但后端仍在处理的体验错位。
- 调整到 240 秒后，与后端图片任务轮询时间更一致。

## 四、小红书文案生成逻辑改动

涉及后端文件：

- `app/api/mp/xhs/generate-v4/route.ts`
- `lib/xhs/generate-v4.server.ts`
- `supabase/migrations/20260509_add_xhs_cover_points.sql`

### 1. 主题允许为空

接口 `topic` 从必填改为可选：

- 用户填写主题：按用户主题生成。
- 用户不填主题：后端自动构建主题。

自动主题优先级：

1. 主推项目 + 内容方向，例如“补水护理避雷”。
2. 门店名称 + 内容方向，例如“某某皮肤管理科普内容”。
3. 通用兜底，例如“美业攻略内容”。

### 2. 后端自动推断门店植入策略

前端不再暴露“门店植入”给员工，后端根据内容方向和上下文自动判断：

- 没有门店上下文：`none`
- 科普：`soft_offer`
- 对比：`local_category_guide`
- 攻略 / 避雷：`store_once`
- 求推荐、本地推荐、哪家好等语境：`recommendation_reply`

策略含义：

- `none`：只写通用干货，不出现店名，不做销售。
- `soft_offer`：围绕主推项目的服务逻辑写，但不硬塞店名。
- `store_once`：正文最多自然出现一次门店昵称，用于说明服务边界或适合人群。
- `local_category_guide`：更适合对比帖，用“三类门店适合不同人”的结构，不虚构具体竞品门店。
- `recommendation_reply`：只在求推荐语境下生成置顶评论，用公开搜索路径承接。

### 3. 置顶评论规则收紧

旧逻辑偏向默认生成置顶评论。今天改为：

- 默认 `pinned_comment` 输出空字符串。
- 只有 `recommendation_reply` 这类求推荐场景才输出置顶评论。
- 置顶评论不得出现：
  - 微信
  - 手机号
  - 二维码
  - 大众点评、抖音等平台直写
  - 明确导流动作

这样符合当前判断：除了求推荐类内容，其他帖子暂时不需要置顶评论。

### 4. 封面短点 `cover_points`

文案模型新增输出 `cover_points`：

- 用于首图上的短清单、小标签、辅助信息点。
- 默认 balanced 档输出 3 个。
- rich 档输出 4 个。
- simple 档不强制输出。

这些短点用于解决用户反馈的“有些封面只有一个标题加底图，太单调”的问题。

数据库新增迁移：

```sql
alter table public.xhs_drafts
  add column if not exists cover_points jsonb not null default '[]'::jsonb;
```

注意：

- 代码已做兼容：如果生产库暂时没有 `cover_points` 字段，更新草稿时会降级跳过该字段，不影响文案和封面生成主流程。
- 但为了草稿恢复后仍能保留封面短点，建议后续在 Supabase 生产库执行该迁移。

## 五、小红书封面生图改动

涉及文件：

- `app/api/mp/xhs/generate-cover-image/route.ts`
- `app/api/xhs/generate-cover-image/route.ts`
- `lib/posters/gpt-image-2.server.ts`
- `tests/xhs-cover-style.static.test.js`

### 1. 固定 1k 生图

封面生图固定：

- `resolution = "1k"`
- 不再接受前端传入 `2k`
- 不再默认走 `2k`

原因：

- 用户明确要求不要继续用 `2k`，因为生成更慢、扣费更高。
- 当前问题不是分辨率，而是 prompt、视觉结构和信息密度不稳定。
- 先把成本固定在 1k，再优化构图和提示词更合理。

### 2. 延长图片生成服务时间

封面生图接口增加：

- `export const maxDuration = 300`

图片任务轮询超时也从默认较短时间提高到 240 秒级别。

目的：

- 减少图片排队时后端函数过早结束。
- 与小程序端 240 秒长请求保持一致。

### 3. 封面质量底线规则

封面 prompt 追加“小程序封面质量底线”：

- 必须是完整的小红书首图设计，不是背景图。
- 可以有人脸、护理场景、局部对比、少量清单或辅助说明。
- 底部必须保持干净。
- 禁止底部导流组件、转化按钮、互动引导、私域联系方式、平台入口、可扫码联系元素。
- 必须有明确视觉焦点、美业质感和手机端可读标题。
- 中文文字不要错字、乱码。

### 4. 支持封面参考图

发文结果页新增封面参考图能力：

- 门店环境
- 项目/仪器
- 人物/案例
- 风格参考
- Logo/门头

后端会把这些素材转成 data URL 传给 `gpt-image-2`，并给模型明确使用规则：

- 风格参考只学习构图、配色、字体气质和信息密度。
- 门店环境用于真实空间氛围或背景质感。
- 项目/仪器图作为局部元素或材质参考，不做硬广产品图。
- 人物/案例图只作皮肤状态、护理动作或人物情绪参考。
- Logo/门头默认只作品牌气质参考，不直接放联系方式、二维码、门头文字。

### 5. 辅助信息点进入封面 prompt

封面生图接口会读取：

- 前端传入的 `coverPoints`
- `preExtracted.points`
- 草稿里的 `cover_points`

然后根据 `coverDensity` 决定首图上要不要加入短点或小标签。

这次专门解决：

- 图三、图四那种“更像小红书首图”的丰富信息结构。
- 避免图二、图五那种“只有干巴大字 + 背景”的单调感。

### 1. 海报也固定 1k

海报生成同样固定基础档：

- 前端分辨率选项只保留 `1k`。
- 后端 `BASIC_POSTER_RESOLUTION = "1k"`。
- 模板默认分辨率均调整为 `1k`。
- `resolution` schema 只允许 `1k`。

目的：

- 避免员工不理解 1k/2k 差异导致费用不可控。
- 把优化重点放在内容、构图和参考图，而不是盲目升分辨率。

### 2. 支持风格参考图

海报素材类型从：

扩展为：

- 风格参考
- Logo/门头
- 门店环境
- 项目/产品
- 人物/案例

前端上传素材时会让用户选择素材类型。

如果选择“风格参考”，系统会提示模型：

- 学习构图
- 学习配色
- 学习字体层级
- 学习留白比例
- 不照抄原图文字、Logo、人物、产品、价格或具体版面

### 3. 新增 P13 节日祝福模板

新增模板：

- ID：`P13`
- 名称：节日祝福
- 场景：客户问候
- 目标：生成一张有温度、不推销的节日问候图
- 适用：端午、中秋、春节、节气、客户群问候
- 默认尺寸：`4:5`
- 默认分辨率：`1k`

问诊模型规则同步更新：

- 用户说祝福、问候、不卖东西、不促销、给老客发节日图时，优先选择 `P13`。
- `templateId` 允许范围从 `P01-P12` 扩展为 `P01-P13`。

### 4. 海报 prompt 高级感增强

模板 prompt 做了更强的视觉约束：

- 强调真实美业门店、品牌大片、杂志感、轻奢、克制留白。
- 区分“可见文案”和“仅用于理解的上下文”。
- 避免把字段名、用途说明、目标人群说明画进海报。
- 对节日祝福类模板，禁止价格、优惠、促销、到店礼包等销售元素。

### 5. Negative prompt 处理方式调整

`gpt-image-2` 的封装函数不再把 negative prompt 当作独立字段发送，而是折叠进主 prompt：

```text
需要避开的画面问题：...
```

原因：

- 之前直接拼 `Negative prompt:` 存在被模型误理解的风险。
- 统一放进中文约束里，更适合当前 APIMart 图像接口的输入方式。

## 十一、后续建议

### 1. 做一轮真实样张验收

建议用 4 个方向各跑 2-3 条真实门店内容：

- 攻略
- 科普
- 避雷
- 对比

每条记录：

- 文案是否自然带店
- 是否误生成置顶评论
- 封面是否有 CTA
- 封面是否过于单调
- 是否稳定为 1k
- 是否能用商家上传的参考图提升质感

### 2. 执行数据库迁移

建议在生产 Supabase 执行：

```sql
alter table public.xhs_drafts
  add column if not exists cover_points jsonb not null default '[]'::jsonb;
```

执行后，旧草稿恢复再生成封面时，信息短点会更稳定。

### 3. 观察 1k 出图质量

今天已把 1k 固定下来，后续应该观察：

- 1k 是否满足小红书首图传播。
- 是否仍有明显文字错误或乱码。
- 是否仍出现 CTA。
- 是否需要增加 OCR 审核和自动重试。

如果需要更强保证，可以后续增加：

- OCR 识别 CTA / 错字
- 自动重试一次
- 对失败图进行风格回退

但这些都会增加耗时和成本，需要单独评估。
